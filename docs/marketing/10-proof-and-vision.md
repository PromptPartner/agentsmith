## Evidence standard

The five proof points below are candidates, not five finished public claims. Each separates:

- what the repository proves now;
- what still needs a marketing asset, user observation, or customer permission; and
- the boundary beyond which the claim would become misleading.

Research about the wider market proves that a problem exists. It does not prove AgentSmith solves
that problem for customers.

## Five proof-point candidates

### Proof candidate 1: one task, one complete evidence chain

| Attribute | Detail |
|---|---|
| **Candidate claim** | AgentSmith turns a coding-agent task into an inspectable chain from accepted scope to changed files, automated checks, real-path exercise, evidence, and handoff |
| **Evidence available now** | The reproducible First Verified Loop bundle shows status coverage, the named baseline failure, bounded change, passing checks, real-path result, receipt, handoff, and zero-drift resume |
| **Asset still required** | Independent newcomer observations before any “beginner-proven” or customer-outcome claim |
| **Current strength** | **Strong technical fixture proof; no user-outcome proof.** The public demonstration is reproducible and its boundaries are explicit |
| **Buying motivations** | Get Comfort; Escape Pain; Achieve Cleanliness/Hygiene |
| **Best use** | Homepage demonstration, README quickstart, deck, launch video |
| **Claim boundary** | The demonstration proves that task and evidence chain, not universal correctness or customer productivity |

**Why it matters:** This is the closest match to “Proof before done.” It is the recommended primary
proof asset because a newcomer can understand it and an expert can inspect it.

### Proof candidate 2: adoption is reversible

| Attribute | Detail |
|---|---|
| **Candidate claim** | AgentSmith tracks the configuration it manages and tests dry run, repeat installation, update planning, rollback, uninstall, and preservation of unrelated settings |
| **Evidence available now** | Installer, ownership, idempotence, update, integrity, rollback, uninstall, doctor, and native operating-system fixture tests |
| **Asset still required** | Native operating-system release evidence beyond the clean and existing-config public fixtures |
| **Current strength** | **Strong technical proof** |
| **Buying motivations** | Get Comfort; Avoid Effort; Achieve Cleanliness/Hygiene |
| **Best use** | Technical evaluation, installation page, developer deck, objections about tool sprawl |
| **Claim boundary** | Tested fixture behavior does not prove every third-party client version or unusual local configuration |

**Why it matters:** Reversibility is difficult to fake with copy. It demonstrates that ownership is a
product behavior rather than a promise to “play nicely.”

### Proof candidate 3: compatibility claims carry evidence levels

| Attribute | Detail |
|---|---|
| **Candidate claim** | AgentSmith distinguishes instruction discovery, skills, Model Context Protocol connections, hooks, and native runtime integration instead of presenting every target as equally supported |
| **Evidence available now** | Machine-readable compatibility registry, strict conformance tests, CLI compatibility report, and isolated evaluation path for Claude Code and Codex |
| **Asset still required** | A public compatibility page generated from the registry, with dates and links to the evidence for each capability |
| **Current strength** | **Strong technical proof; moderate buyer proof** |
| **Buying motivations** | Get Comfort; Save Time; Achieve Cleanliness/Hygiene |
| **Best use** | GitHub, technical documentation, comparison content, evaluator review |
| **Claim boundary** | Claude Code and Codex have the deepest native evidence. Certification targets are not equal native integrations |

**Why it matters:** The proof is not the number of supported agents. It is the willingness to show
exactly what “support” means and where it stops.

### Proof candidate 4: autonomous work has a stop condition

| Attribute | Detail |
|---|---|
| **Candidate claim** | AgentSmith can run one accepted item through isolated maker/checker attempts with scope controls, finite retries, collision detection, durable interruption, and no push or merge authority |
| **Evidence available now** | Autonomous state and controller suites cover acceptance gates, mutation detection, attempt caps, locks, collisions, stop/resume, stale recovery, and local-only completion |
| **Asset still required** | One honest autonomous-run diary showing the accepted scope, checks, attempts, any rejection or intervention, final state, and authority boundary |
| **Current strength** | **Strong mechanism proof; no customer-outcome proof** |
| **Buying motivations** | Save Time; Get Comfort; Avoid Effort |
| **Best use** | Advanced documentation, developer content, deck vision-to-current-state transition |
| **Claim boundary** | This is not multi-ticket orchestration, automatic integration, remote delivery, or an autonomous software factory |

**Why it matters:** “It knows when to stop” is more credible and useful than a vague claim about
working autonomously for hours.

### Proof candidate 5: discipline used in real delivery

| Attribute | Detail |
|---|---|
| **Candidate claim** | AgentSmith grew from long-running product work and repeat PromptPartner delivery rather than from a prompt collection assembled for launch |
| **Evidence available now** | First-party report of more than eight months of AI Admin Panel development and more than ten PromptPartner customer projects using the wider framework or related AI-foundation components |
| **Asset still required** | Dated artifacts, selected before/after evidence, contributor attribution, measurable outcomes, publication permission, and a precise definition of which projects used which AgentSmith surfaces |
| **Current strength** | **Weak for publication today; potentially strongest commercial proof** |
| **Buying motivations** | Get Comfort; Increase Social Status; Save Time; Make Money |
| **Best use** | Case studies, PromptPartner website, deck, workshops, founder narrative |
| **Claim boundary** | Do not publish the duration, customer count, avoided defects, or outcomes until the supporting records and permissions match the exact wording |

**Why it matters:** Repository proof shows that the mechanism works as designed. Delivery evidence is
what can eventually show that it matters outside this repository.

## Recommended proof sequence

Do not wait for every customer case before publishing anything. Build proof in layers:

1. **Now:** expose the reproducible repository checks, reversible lifecycle, compatibility contract,
   and bounded-autonomy tests.
2. **Next:** use the completed one-task sandbox demonstration, then produce the autonomous-run diary.
3. **Then:** publish the AI Admin Panel trace and permission-safe PromptPartner cases as the evidence
   becomes complete.

The recommended first proof block is:

> **Open source. Project-owned. Reversible. Verified in public.**  
> Inspect the rules, run the checks, and see the current limits in the repository.

This is safe only when each phrase links to the corresponding source or demonstration.

## Five product-vision options

### Vision 1: dependable AI-assisted work

> **A future where any professional can use capable AI agents for consequential work and still know
> what changed, why it is acceptable, and what happens next.**

**Strategic emphasis:** Trustworthy outcomes without arguing against better models.  
**Connection:** Proof — Control — Continuity; all primary audience paths.  
**Risk:** Broad enough that AgentSmith must show concrete coding examples to avoid sounding generic.

### Vision 2: responsible agency for new builders

> **A future where people can turn their expertise into working software without coding blind, while
> learning enough to direct, verify, and own the result.**

**Strategic emphasis:** Open professional software creation without claiming expertise is obsolete.  
**Connection:** Guided first use, selective learning, recovery, and ownership.  
**Risk:** May make experienced developers assume the product is mainly educational.

### Vision 3: portable engineering discipline

> **A future where engineering discipline belongs to the project—not one model, tool, chat, or
> expert—and travels wherever the work goes.**

**Strategic emphasis:** Durable, project-owned quality across changing agents and teams.  
**Connection:** Canonical rules, verification, compatibility, continuity, and reversible lifecycle.  
**Risk:** “Engineering discipline” narrows the broader office-work profile story and may sound formal
to first-time builders.

### Vision 4: autonomy earned through evidence

> **A future where every project can earn more autonomy one verified step at a time, while people
> retain authority over the outcome.**

**Strategic emphasis:** A credible path toward the software-factory aspiration without surrendering
control.  
**Connection:** Progressive rigor, verification, maker/checker, worktrees, and stop conditions.  
**Risk:** Pulls attention toward an advanced feature before onboarding and adaptive verification are
ready.

### Vision 5: open infrastructure from creation to ownership

> **A future where open, inspectable control layers connect how AI-assisted work is specified, built,
> verified, operated, and ultimately owned.**

**Strategic emphasis:** An ecosystem arc from AgentSmith and PromptPartner delivery toward AI Admin
Panel as a future operating environment.  
**Connection:** Open source, delivery discipline, ownership transfer, and the future hosting bridge.  
**Risk:** Furthest from what AgentSmith alone can prove today and easiest to confuse with a platform
claim.

## Vision recommendation

Use **Vision 1: dependable AI-assisted work** as the shared product vision:

> **A future where any professional can use capable AI agents for consequential work and still know
> what changed, why it is acceptable, and what happens next.**

It is human-centered, includes both communication paths, and remains useful as models improve. It
also maps cleanly to the three pillars without reading like a feature list:

- **what changed** → Control;
- **why it is acceptable** → Proof; and
- **what happens next** → Continuity.

Use the other visions as secondary lenses:

- Vision 2 for the guided learning path.
- Vision 3 as the technical north star.
- Vision 4 for the autonomy roadmap.
- Vision 5 for the PromptPartner and AI Admin Panel ecosystem horizon.

The recommendation remains provisional until it is tested with both first-time professional builders
and experienced developers.

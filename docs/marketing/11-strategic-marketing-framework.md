## Executive strategy

AgentSmith should not compete with Claude Code, Codex, or future models on intelligence. It should
make their growing capability safer and more useful for consequential work.

The product position is:

> **The portable control-and-evidence layer for AI-assisted work.**

For technical software-development audiences:

> **An open-source, agent-native software development lifecycle harness.**

The launch message is:

> **Your AI agent is capable. Prove the result.**  
> **Proof before done.**

The three promises are:

1. **Proof:** Prove it works.
2. **Control:** Keep it in scope.
3. **Continuity:** Continue without starting over.

AgentSmith is open-source infrastructure developed from PromptPartner's delivery practice. It is a
lead magnet and a delivery component, not a separate paid service. The approved commercial wording
is:

> **Included and tailored at no additional licence cost in relevant PromptPartner projects.**

## Audience and market focus

### Primary: technically curious first-time professional builder

Typical users include designers, founders, product managers, operators, marketers, analysts,
consultants, and other domain experts. They can describe a real problem and are willing to learn a
limited amount, but they are not professional software developers.

Their common trigger is not curiosity about another framework. Something has gone wrong:

- a quick prototype has become important but difficult to maintain;
- an agent changed more than requested;
- “almost right” output started an endless repair loop;
- they discovered too late that a specification, test, or recovery point was needed;
- they cannot prove that the result works; or
- a colleague says non-developers should not use coding agents.

The response should neither gatekeep nor promise that expertise no longer matters. AgentSmith helps
them build with clearer boundaries and evidence, while showing when qualified review is required.

### Secondary: experienced agentic developer

Typical users include solo developers, technical founders, senior engineers, engineering leads, and
AI-enabled consultancies. They already understand software delivery. Their problem is repeated
setup, inconsistent agent behavior, incomplete verification, lost context, or unsafe autonomy.

They need a small, inspectable baseline rather than another large methodology. Lead with technical
evidence, ownership, and exact boundaries. Do not teach basic concepts they already know.

### Audience sequence

Professionals come first because a real work problem creates urgency, proof, and a credible path to
PromptPartner. Students and hobbyists remain important as a later learning and community path. They
should not force the first launch to speak equally to everyone.

| Priority | Customer need | Current failure | AgentSmith response |

| 2 | Preserve intent and progress | The project outgrows one conversation and decisions must be reconstructed | Specifications, decisions, handoffs, research, feedback, and durable evidence |
| 3 | Escape almost-right repair loops | Each correction creates another regression or broader change | Small accepted scope, failing check first, complete verification, and recovery points |

| 6 | Reuse a quality bar | Each repository and agent receives another private pile of rules | Canonical project contract, profiles, adapters, and managed lifecycle |

| 8 | Avoid process theatre | Heavy methods add more vocabulary and artifacts than the task needs | Progressive rigor and task-specific guidance loaded only when needed |

## Value proposition

For professionals using AI agents to build real work who need more than a fast first draft,
AgentSmith is an open-source, portable control-and-evidence layer that keeps work scoped, verified,
resumable, and reversible. Unlike relying on a coding agent alone, AgentSmith makes the project's
operating rules, evidence standard, memory, and path to bounded autonomy explicit and owned by the
project.

### First-time-builder version

> AgentSmith adds a clear plan, boundaries, proof, and a recovery path around the coding agent you
> already use. It teaches the next useful concept when it matters without pretending expertise is no
> longer necessary.

### Experienced-developer version

> AgentSmith makes your engineering discipline portable across projects and coding agents: one
> inspectable contract for scope, verification, continuity, reversible configuration, and bounded
> autonomous work.

### Why this remains relevant as models improve

Better models reduce implementation friction. They do not remove project-specific intent,
authority, evidence, ownership, or responsibility. AgentSmith should remove guidance that models
reliably perform without it, while retaining the external contract that defines what this project
means by correct and complete.

## Strategic narrative

### The shift

Capable coding agents are becoming normal tools. More people can create useful software, and
experienced developers can delegate larger pieces of work.

### The tension

Generating a first version became easier. Responsibility for the outcome did not disappear. A
polished result can still contain incorrect data, missing authorization, incomplete edge cases, or
unexercised background work. A long session can lose an earlier decision. A capable agent can finish
the wrong scope.

### The new model

Let the agent reason and execute. Let the project own the contract around it:

1. state one bounded outcome;
2. show the plan and affected scope;
3. run checks that fit the repository;
4. exercise the result where a person or downstream system sees it;
5. preserve the evidence, decisions, and next step; and
6. increase autonomy only when the same contract can check the work independently.

This is progressive rigor. A small repair gets a small loop. Customer-facing or autonomous work gets
stronger gates.

### The analogy

A more powerful engine makes good brakes, instruments, and a route more important, not less.
AgentSmith is that control layer around the agent. Use the analogy sparingly and explain the concrete
mechanism immediately after it.

## Content architecture

### Pillar 1: Proof — 40% of launch content

**Promise:** Prove it works.

Cover the difference between running and proving, automated tests versus real-path exercise versus
judgment, adaptive verification, continuous-integration fit, security boundaries, evidence
receipts, honest case evidence, and before/after demonstrations.

### Pillar 2: Control — 35% of launch content

**Promise:** Keep it in scope.

Cover small specifications, non-goals, plans before changes, permissions, diff inspection, Git
checkpoints in plain language, reversible installation, configuration ownership, recovery, and the
boundary between safe learning and expert review.

### Pillar 3: Continuity — 25% of launch content

**Promise:** Continue without starting over.

Cover durable specifications and handoffs, decisions, profiles, portable working agreements,
feedback loops, context loss, attended-to-autonomous progression, isolated worktrees, and the future
AI Admin Panel bridge.

### Repeatable content formats

- **One task, one evidence chain:** scope → change → automated checks → real-path exercise → receipt
  → handoff.
- **Almost right:** inspect a plausible result and expose what the first green signal missed.
- **Inside the boundary:** show an unrequested change being surfaced or rejected.
- **Fresh-session resume:** stop and continue without retelling the old conversation.
- **Autonomy diary:** show scope, attempts, checker decisions, intervention, and the stop condition.
- **Small concept, real consequence:** explain one specification, Git, verification, or permission
  concept through a concrete task.

## Proof strategy

### Lead proof: one task, one complete evidence chain

The first major asset should show a small, visible defect in a prepared repository:

1. reproduce the failure;
2. write the short specification and non-goals;
3. show the plan and expected files;
4. make the bounded change;
5. run automated checks;
6. exercise the user-visible path;
7. inspect the diff and evidence receipt;
8. show recovery; and
9. resume from a fresh session.

This demonstrates the product's complete value without claiming universal correctness or measured
productivity.

### Supporting proof

| Proof | Current strength | Next asset |
|---|---|---|
| Reversible adoption | Strong technical proof | Clean-project and existing-config install/update/uninstall demonstration |
| Compatibility evidence levels | Strong technical, moderate buyer proof | Public page generated from the registry with dates and evidence links |
| Bounded autonomy with a stop condition | Strong mechanism proof | Honest run diary including rejection or intervention |
| Real-delivery discipline | Weak for publication today | AI Admin Panel trace and permission-safe PromptPartner evidence cards |

The candidate proof block is:

> **Open source. Project-owned. Reversible. Verified in public.**

Use it only when each phrase links directly to supporting evidence.

## Product vision

### Shared vision

> **A future where any professional can use capable AI agents for consequential work and still know
> what changed, why it is acceptable, and what happens next.**

This maps directly to Control, Proof, and Continuity. It is broad enough for both audience paths and
remains relevant as models improve.

### Supporting vision lenses

- **Learning:** People can turn expertise into working software without coding blind, while
  learning enough to direct, verify, and own the result.
- **Technical:** Engineering discipline belongs to the project—not one model, tool, chat, or expert—
  and travels wherever the work goes.
- **Autonomy:** Every project can earn more autonomy one verified step at a time while people retain
  authority over the outcome.
- **Ecosystem:** Open, inspectable control layers can eventually connect specification, creation,
  verification, operation, and ownership.

## Launch and production plan

### Phase 1: make the promise true and easy to see

- Build adaptive verification and its coverage explanation.
- Clarify central, project, profile, and generated state.
- Produce the guided sandbox and simplify continuity.
- Define the exact evidence contract for the first public demonstration.

**Exit condition:** a new user can complete one verified loop and explain what was proven and what
was not.

### Phase 2: update the product documentation

- Rewrite the README opening around the selected headline, promises, and primary call to action.
- Add separate first-time-builder and experienced-developer paths.
- Explain installation scope and profile choice with one mental model.
- Add the verification coverage map and claim boundaries.
- Keep advanced autonomy visible but below the attended first loop.

**Exit condition:** README, quickstart, reference documentation, and actual product behavior agree.

### Phase 3: produce the proof assets

- Record the complete one-task evidence chain.
- Publish reversible lifecycle and compatibility evidence.
- Publish one honest bounded-autonomy diary.
- Reconstruct the AI Admin Panel trace.
- Complete two permission-safe PromptPartner evidence cards.

**Exit condition:** each public proof claim links to an inspectable artifact.

### Phase 4: produce the launch package

- Minimal PromptPartner-branded presentation with diagrams.
- GitHub launch page and repository visuals.
- Founder launch article.
- Reddit-first discussion material based on real problems, not promotional claims.
- Technical comparison article for audiences evaluating methods and orchestration tools.
- PromptPartner website bridge using the existing service journey.

**Exit condition:** every asset uses the same position and routes to the correct next action.

### Phase 5: learn and adapt

- Observe activation, recovery, and transfer into real projects.
- Measure which proof assets lead to meaningful repository use and PromptPartner conversations.
- Test the working headline, tagline, category language, and vision with both audience paths.
- Remove claims or guidance that evidence does not support.
- Review the harness as model capability changes; delete redundant instructions only after a
  behavioral evaluation shows no regression.

**Exit condition:** product and message changes are tied to observed evidence rather than attention
metrics alone.

## Claim and editorial guardrails

- Name the evidence whenever using “proof,” and state what it does not cover.
- Do not publish quantified productivity, quality, cost, security, or customer outcomes without
  matching evidence.
- “Beginner-friendly” remains a target until observed sessions support it.
- “Works across agents” must state that Claude Code and Codex have the deepest native evidence.
- “Control” does not mean perfect obedience in attended sessions.
- “Continuity” means durable project artifacts, not infinite model memory.
- “Autonomous” always names scope, attempts, checks, stop condition, and authority boundary.
- Do not imply AgentSmith replaces expertise, security engineering, continuous integration, native
  sandboxes, product management, or orchestration engines.
- Do not shame people for vibe coding. Explain the point where a prototype becomes consequential.
- Avoid raw counts of profiles, skills, agents, tests, or GitHub stars as the main value story.
- Use plain international English, short sentences, and concrete examples. Explain abbreviations.
- Use analogies to introduce a mental model, then return immediately to the real mechanism.
- Keep named competitor comparisons in technical material, not the main presentation.

## Success measures

Do not optimize for GitHub stars alone. Measure the complete path.

| Stage | Useful measure |
|---|---|
| Discovery | Qualified visits from practitioner discussions and PromptPartner content |
| Evaluation | Dry runs, compatibility-page visits, proof-demo completion, and repository inspection |
| Activation | First verified loop completed; user can explain evidence and recovery |
| Transfer | User identifies and completes one bounded task in a real project |
| Retention | Fresh-session resume, repeated verify use, profile reuse, and safe update behavior |
| Community | Issues or contributions tied to real use rather than feature requests without context |
| Commercial | Qualified PromptPartner conversations where the need extends beyond the harness |
| Product learning | Verification gaps, state confusion, recovery failures, and guidance proven redundant |

Targets should be set only after a baseline exists.
